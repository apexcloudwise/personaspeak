# ADR-0011: Opt-In Suggested Replies from Notification Context

**Status:** Accepted (2026-09-02, Phase 2 #120/#121)

## Context

ROADMAP Phase 2 ships the wow feature: the keyboard drafts replies to the message you just received, before you type anything. Doing that means the keyboard must learn about incoming messages, which touches the strictest line in our privacy posture (ADR-0005): a keyboard that reads message content is one clipboard permission away from being a diary. The feature must earn the data it touches, in public, with the code as the receipts.

Two implementation facts forced design decisions:

1. **The reply case lands on an empty editor.** The rewrite flow (M3) captures a snapshot and replaces it under staleness guards. A suggested reply is normally applied to an *empty* editor, where `captureSnapshot()` returns `EmptyInput` and `attemptReplace` is not applicable — there is no prior content to guard against drift on.
2. **The N-replies contract must not churn the adapter layer.** `ProviderAdapter` (ADR-0009) returns one completion per call. Rewriting that interface for `List<String>` would tax every adapter for one feature.

## Decisions

### 1. Notification access is the single switch — opt-in, structural, no stored flag

Nothing is read until the user grants notification access in the system screen. There is deliberately **no separate in-app preference toggle**: system notification access *is* the preference. Revoking access in system settings removes the data source and the listener's `onListenerDisconnected`/teardown wipes the in-memory store. "Off by default" is therefore structural — there is no flag that can be flipped accidentally — rather than a stored default.

An in-app consent gate (prominent disclosure: what is read, what is kept, what we never do) is shown **before** the deep link to `ACTION_NOTIFICATION_LISTENER_SETTINGS`, per Play User Data policy. The disclosure lives in the feature's flow, not the listing or the privacy policy.

### 2. Message content is RAM-only, LRU-capped, forgotten on reply

- The store (`IncomingMessageStore`) is a pure-Kotlin, process-wide singleton holding the latest incoming message per conversation: no disk, no logs, no telemetry, no backup surface (nothing to back up — it never leaves RAM).
- LRU cap of 5 conversations; latest-wins per conversation key.
- Applying a suggestion forgets that conversation's message ("forgotten on reply"); dismiss keeps it for a retry.
- Notification text is never logged. `verify-no-secret-logging.sh` stays green.

### 3. We read to draft — never send

No auto-send, no marking-as-read, no `RemoteInput` replies, no notification actions. The feature's entire output is *editable text placed in the user's own editor*, reviewed by the user, sent by the user's own hand in their own messaging app.

### 4. Egress only on an explicit generate tap, per ADR-0009

Suggestions are generated by the active provider. Unconfigured (the default), that is `FakeProvider` — fully offline, zero egress. With a BYOK provider configured, the explicit suggestion-generate tap sends the persona prompt + incoming message text to the user's configured provider over the ADR-0009 path (HTTPS, pinned endpoints, OpenRouter proxy disclosure retained verbatim in spirit). No credential ever touches the notification path.

### 5. `EditorPort.insertDraft(text)` — one verified mutation, typed identically

The port gains `suspend fun insertDraft(text: String): ReplaceResult`:

- Exactly one editor mutation, post-write read-back verified, same `ReplaceResult` typing as `attemptReplace`.
- Contract: if the editor is observed non-empty (or sensitive/unsupported) at insert time, `insertDraft` returns `WriteRejected` without mutating — the coordinator routes those cases through the existing snapshot-guarded `attemptReplace` path instead, so a suggestion replaces the user's draft exactly like a rewrite.
- **Why this is not a staleness violation:** staleness guards protect prior editor content from being clobbered by a late write; with an empty editor there is no prior content, so the guards have nothing to compare. Mutation-count honesty is not waived — still exactly one mutation, still read-back verified, and the coordinator only calls `insertDraft` immediately after a capture that returned `EmptyInput`.
- No new result type: the reply case shares `AppliedVerified`/`WriteRejected`/`WriteUnconfirmed` with rewrite so upstream error handling stays one taxonomy.

### 6. N replies ride inside the prompt, parsed by `NumberedSuggestions`

`CompletionProvider.suggest(system, text, count)` carries the N-replies contract in the prompt (numbered lines); `NumberedSuggestions` parses one completion back into N replies (lenient: ≥1 parseable line succeeds; 0 fails). `ProviderAdapter` and both HTTP adapters are untouched.

## Consequences

- `:ime:app` manifest declares `ReplyNotificationListener` with `android.permission.BIND_NOTIFICATION_LISTENER_SERVICE` (system-bound only), ledgered in `UPSTREAM-MODIFIED.md`.
- `:core-personas` gains `IncomingMessageContext` + `PromptBuilder.buildSuggestionPrompt` (pure Kotlin, golden-pinned against the Python reference via `desktop/personaspeak.py --suggest`).
- The reply strip states (`Suggesting`, `Suggestions`), chip, regenerate, apply-through-`insertDraft`, and forget-on-apply live in `:personaspeak-ui` behind the existing `RewritePanelState` machine; `StitchError` gains a `ReplyContextGone` variant for a context that evaporates mid-flow.
- The release fail-closed gates (`ReleaseActiveCompositionTest`, `ReleasePrivacyAndEgressAuditTest`) are extended, never weakened: default composition and rewrite privacy claims are untouched.
- Demo quality offline is a `FakeProvider` obligation: deterministic, three distinct registers, no network.
